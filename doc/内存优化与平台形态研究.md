# 内存优化与平台形态研究 — LLM 架构可视化网站(计划补充篇)

> 主题:① 利用架构中的重复性(N 个相同 decoder layer、相同 attention 子结构、数百个相同 MoE 专家)把网页内存压到最低;② 按模型规模分级提供动画等重功能;③ 网页之外的内存友好平台形态。
>
> 编制日期:2026-07-30 · 基于两个独立调研 agent 的核实结果(来源见文末)

---

## 一、结论摘要

1. **5 万个"长方体"本身根本不贵**:用 1 个共享 BoxGeometry + 1 个 InstancedMesh,DeepSeek-V3 全展开(约 5 万实例)的渲染数据 CPU+GPU 合计只要 **8–12 MB、1 个 draw call**。真正会把内存搞爆的是三件别的事:每节点一个 Mesh/JS 对象(≈75–100 MB 堆 + 5 万 draw call,死刑)、8.9MB index.json 的解析残留(峰值 40–80 MB)、高分屏 framebuffer(手机上 MSAA×高 dpr 可达 100MB+)。
2. **"减少重复 attention / 重复层"要在三个层面同时做**(见第二节):IR 层只存"原型 × 重复计数"(<50KB)、渲染层 GPU 实例化、UI 层默认折叠 + 懒展开。三层做完,默认视图只有 ~2000 个实例。
3. **动画按模型规模分级**(你的新要求,完全正确,已纳入方案):动画的真实成本不是几何而是**持续渲染循环**——静态视图可以用 `frameloop="demand"` 把 GPU/电量降到近零,动画一开就回到每帧全量渲染。所以大模型禁用全局动画、只在"单层聚焦"里做局部动画,是内存/功耗曲线上最划算的一刀(第四节给了具体分级表)。
4. **移动端是真红线**:2026 年实测 iPhone SE 3 单页约 **100 MB**、iPad 8 约 200 MB 即崩,且 iOS 没有任何内存监控 API。手机默认给 2D 分层图(hfviewer 式),3D 是"可尝试"而非默认。
5. **平台组合推荐**:网页(主)+ Tauri 桌面壳(重度用户逃生舱,复用同一构建产物)+ anywidget/pip(研究者渠道)+ 移动 2D 保底;放弃 Electron、像素流、Bevy 原生重写。**预烘焙资产 + 流式 LOD 提升为 P0 架构决策**(不是可选优化)。

## 二、核心策略:把"重复"吃干榨净(重点回答你提的方向)

模型架构的重复性有三级:层级(61 个 decoder layer 中 58 个完全同构)、层内(每层的 attention 子结构相同)、专家级(256 个专家逐个同构)。对应三层去重:

### 1. IR 数据层:原型 + 重复计数(不是存 N 份)

```
ArchGraph
├─ densePrototype   (×3)   ~10 节点
├─ moePrototype     (×58)  attention 12 节点 + 共享专家 3 节点
│    └─ expertPrototype (×256)  gate/up/down 3 节点
└─ 全局节点 (embedding / final_norm / lm_head)
```

- IR 本体 **< 50 KB**(对比:5 万节点每个建 JS 对象 ≈ 15–25 MB)。世界坐标不存储,由 `原型局部坐标 + 层偏移 + 专家网格偏移` 现场计算;需要缓存时用 SoA TypedArray(~40 B/节点,5 万节点 2 MB)。
- 张量名不存 5 万个字符串(~6–8 MB),存**模板 + 参数**:`model.layers.{i}.mlp.experts.{j}.gate_proj.weight` → 模板表 <100 条,每节点 4 字节(templateId+i+j),合计 **<300 KB**,tooltip 显示时现拼。
- 8.9MB 的 index.json 在 **Web Worker 里解析 → 构建 TypedArray IR → Transferable 零拷贝传回 → `worker.terminate()`**,解析峰值随 Worker 堆整体销毁,主线程只留 ~3 MB。更进一步:对已知架构家族,**根本不需要 index.json——config.json(2KB)就能程序化生成全部结构**(bbycroft 也是纯程序化生成)。

### 2. 渲染层:GPU 实例化(重复几何只上传一次)

- **全场景 1 个 BoxGeometry(<1KB)+ 1–2 个共享材质 + 1 个预分配 InstancedMesh**。每实例只占 64B 矩阵 + 4–12B 颜色/ID;轴对齐盒子还可用 pos+scale 6 个 float 的自定义 attribute 替代 16 float 矩阵,再省 60%。
- 原生 InstancedMesh 两个坑必须绕:**raycast 是 O(n) 线性**(5 万实例 hover 会卡死)→ 点击用 GPU 颜色拾取(零额外内存)、hover 用 SoA AABB 暴力测试 + 30Hz 节流;**视锥剔除是整体的** → 需要逐实例剔除时用 [InstancedMesh2](https://github.com/agargaro/instanced-mesh)(实测支持千万级实例)。
- BatchedMesh 不用(几何 100% 同质时 InstancedMesh 完胜,且 BatchedMesh 需预留顶点容量浪费 VRAM)。纹理开销 ≈ 0(纯色块);真正的 GPU 大头是 framebuffer → **dpr 上限 1.5–2、关 MSAA**。

### 3. UI 层:默认折叠 + 懒展开 + 预分配槽位(零 GC)

- 默认视图:**1 个展开的样板层 + 其余层渲染成 "×58" 聚合堆叠体,总实例 <2000**;MoE 专家默认聚合成一块"专家阵列"体素(标注 top-k 路由),点击才展开。
- 展开不是"新建 Mesh",而是**往预分配的 InstancedMesh 空槽写 TypedArray + 改 count**;折叠就是把 count 减回去。零对象创建、零 GC、零 dispose——从根上绕开 three.js 的 dispose 三连坑(`scene.remove()` 不释放 GPU 内存;dispose 后残留引用会自动重新上传;shader program/renderList 有独立缓存)。
- 同时展开层数上限 K(如 3),超出 LRU 折叠最旧的层。全量 5 万实例只在用户显式"全部展开"(且仅桌面档允许)时出现。
- 用 `renderer.info.memory` 做 CI 回归断言,防泄漏。

## 三、按模型规模分级的能力策略(动画分级)

动画成本的本质:静态视图可用 **`frameloop="demand"`**(r3f 官方支持)——不交互就完全停止渲染循环,GPU 占用与耗电近零;任何常驻动画(数据流粒子、呼吸高亮)都会强制回到 60fps 持续渲染,手机上还引发发热降频。所以**分级的第一刀砍的就是"全局常驻动画"**:

| 档位 | 判定(按 IR 估算,可配置) | 视图 | 动画 | 展开 |
|---|---|---|---|---|
| **T0 教学级** | 总参数 < ~0.5B 且层数 ≤ 24(GPT-2、nanoGPT 级) | 全展开 | ✅ 全功能:数据流动画 + 相机游览 + 逐步讲解 | 无限制 |
| **T1 常规** | < ~15B、非巨型 MoE(Llama-8B、Qwen-7B 级) | 默认折叠,可全展开 | ✅ 默认开,可关;`demand` 模式下动画只在播放时激活 | K=5 层 |
| **T2 大型** | 15B–100B 或专家数 ≥ 64(Qwen3-30B-A3B、Mixtral 级) | 折叠 + 聚合 | ⚠️ **无全局动画**;仅"单层聚焦模式"内提供局部数据流动画(单层几百实例,成本恒定) | K=3 层 |
| **T3 超大** | > 100B(DeepSeek-V3、Kimi-K2 级) | 静态 LOD + 聚合,流式加载 | ❌ 完全静态(悬停高亮这类单帧响应保留) | K=2 层,禁全展开 |

- 关键设计:**"单层聚焦"让动画成本与模型大小解耦**——不管 61 层还是 12 层,聚焦模式里永远只动画一层(几百实例),所以 T2/T3 用户仍能看到 bbycroft 式的数据流演示,只是范围受控。
- 档位同时联动:标签数量上限、BVH 是否构建、移动端直接整体降一档(手机上 T1 按 T2 处理,T3 建议切 2D 视图)。
- 阈值放配置文件,上线后按崩溃遥测数据调。

## 四、内存预算表(独立 agent 核实/估算)

**手机档(自守 ≤250 MB,iOS 实测崩溃线 100–200 MB)**

| 项 | 预估 |
|---|---|
| React + three.js 基础堆 | 30–50 MB |
| IR(SoA + 名字模板化) | <3 MB |
| 实例数据(默认 ~2000,展开上限 1 万) | 2–4 MB |
| SDF 字体图集 + ≤100 个标签(troika) | 5–10 MB |
| framebuffer(dpr≤1.5、无 MSAA) | 15–40 MB |
| **合计** | **~60–110 MB** |

**桌面档(自守 ≤500 MB)**:全展开 5 万实例也只到 **~150–270 MB**(大头是 framebuffer 60–150 MB),瓶颈在交互帧率而非内存。

三大风险:iOS 总量红线远低于直觉(且无监控 API,只能崩溃标记遥测 + context lost 恢复);展开/折叠循环若走"新建/销毁"路线必泄漏(预分配槽位根治);5 万实例的原生 hover raycast 会以"卡死"毁掉体验(GPU 拾取 + AABB 暴力根治)。

## 五、网页之外:平台形态推荐

| 层级 | 形态 | 理由与要点 |
|---|---|---|
| **主形态** | 网页 SPA,**以"预烘焙资产 + 流式 LOD"为 P0 前提** | 热门模型服务端预解析布局(同一套布局代码跑 Node),客户端按视口流式加载、视口外淘汰(学 Cesium 3D Tiles / rerun 的显式内存预算思路);内存与模型大小解耦,冷启动秒开 |
| **第二形态** | **Tauri v2 桌面壳**(同一 Vite 产物直接装壳) | 价值不在壳省内存(大头是场景本身),而在**无 tab 级内存上限、不被系统随手杀、本地缓存模型文件**;包体 ~10MB vs Electron ~250MB。坑:Linux WebKitGTK 的 WebGL 不可靠,需内置 2D 降级开关 |
| **第三形态** | **anywidget**(`pip install`,Jupyter/Colab/VS Code 通吃) | 增量只有主代码量的 5–10%;Python 内核侧直接用本地 HF token 和 safetensors 解析,前端只收布局结果,**前端内存反而更低**;精准命中研究者人群 |
| **移动保底** | 同页 **2D SVG/Canvas 分层图**(hfviewer 式),按 `deviceMemory`/WebGL 能力自动切换 | 2D 视图只是同一布局数据的另一个渲染器,2–4 周工作量;手机默认 2D + "尝试 3D"按钮 |
| **放弃** | Electron(被 Tauri 全面替代)、像素流(每并发用户独占 GPU 会话 >$0.7/时,免费工具商业不成立)、Bevy/wgpu 原生重写(需重写全部渲染层,且 wasm 版仍撞浏览器内存墙) | — |

**代码复用路径**:core 包(解析 + 布局 + 场景数据结构,占 70%+)→ 网页 / Tauri / anywidget 共用同一构建产物;烘焙管线 = 同一布局引擎跑在服务端;唯一不复用的是 2D 渲染器(恰好也最便宜)。WebGPU 双后端**不做**(本场景 1–5 个 draw call,WebGL 不是瓶颈;需要时用 three.js WebGPURenderer 白拿回退)。

## 六、对主计划的修订项

1. **新增 P0 架构决策**:预烘焙资产 + 流式 LOD + 显式内存预算管理器(rerun 式 `--memory-limit` 思路)进入 MVP 设计,不后置。
2. **MVP 验收标准追加**:DeepSeek-V3 在 8GB 内存笔记本 Chrome 中 <300 MB、60fps;iPhone 上默认进 2D 视图不崩。
3. **能力分级表(第三节)进入产品规格**,阈值可配置 + 崩溃遥测调参。
4. 里程碑微调:M0 即用"预分配 InstancedMesh + 槽位复用"骨架(避免日后重构);V1 增加 Tauri 壳与 anywidget(各 +1–2 周);2D 降级渲染器排入 V1。
5. 渲染实现细则入库:1 geometry / 1 material / 1 InstancedMesh、GPU 拾取 + AABB hover、troika 懒标签 ≤300、dpr 压制、`frameloop="demand"`、context lost 恢复、`renderer.info.memory` CI 断言。
